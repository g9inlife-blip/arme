# 2026-09-29 인게임 네트워크 요청 경로 분석

## 결론

로그인 이후 던전/우편/뽑기 메뉴에서 기존 `justice_hook.js`의 `UnityWebRequest` 로그가 추가되지 않은 이유는, 인게임 요청이 HTTP `UnityWebRequest` 계층이 아니라 `Alioth.S1.Net` 게임 프로토콜 계층을 사용하는 구조이기 때문이다.

```text
[로그인]
ProtocolGame_HttpRequest
  -> UnityWebRequest
  -> HTTPS

[인게임]
ProtocolGame_SendRequest.<기능>
  -> CSBehaviour.RequestOp(OpInfo)
  -> NetworkCenter.Send
  -> KCPTube / TCPTube
  -> Game Server :8000
```

## 1. CSBehaviour.RequestOp

대상:

`CSBehaviour.RequestOp @ 016dcafc`

Calls IN에 다음과 같은 게임 요청 함수들이 직접 연결되어 있다.

| 기능 | 함수 | RVA |
|---|---|---:|
| 게임 서버 로그인 | Login | 00dde818 |
| 우편 목록 | GetMails | 00de0298 |
| 우편 보상 | MailGetReward | 00de01c4 |
| 스테이지/던전 목록 계열 | GetSections | 00ddea78 |
| 전투 시작 | CreateBattle | 00dded04 |
| 전투 스킵 | SweepBattle | 00ddede0 |
| 전투 결과 | GetBattleReport | 00de1ab8 |
| 상점 목록 | GetShops | 00de1dc4 |
| 상점 구매 | Shopping | 00de1e80 |
| 활동/이벤트 | GetActivities | 00de1f68 |

따라서 사용자가 실제로 실행한 던전과 우편 기능도 현재 추적 대상인 `ProtocolGame_SendRequest` 계층에 존재한다.

## 2. RequestOp -> NetworkCenter

`CSBehaviour.RequestOp @ 016dcafc`의 핵심 호출은:

```text

    ↓
CSBehaviour.RequestOp
    ↓
Alioth.S1.Net.NetworkCenter.Send @ 015b3764
```

이다.

즉 인게임 요청은 `UnityWebRequest`를 새로 생성하는 방식이 아니다.

## 3. NetworkCenter 송신

`NetworkCenter.TrySendRequest @ 015b3df8`는:

```text

  ↓

  ↓
Request.get_Req()
  ↓
Tube 목록 순회
  ↓
Tube 송신 virtual call
```

구조를 가진다.

따라서 실제 게임 패킷이 만들어져 나가는 최종 계층은 `KCPTube/TCPTube`이다.

## 4. 응답 경로

`NetworkCenter.TryHandleResponse @ 015b41e0`에서는:

```text

  ↓
Request.SetResponse(OpInfo)
  ↓
등록 callback
  ↓
DataCenter.ProccessRequestRes @ 016e203c
```

가 확인된다.

따라서 이후 응답 분석은 HTTP response가 아니라 `OpInfo` 생성/복원 및 `DataCenter.ProccessRequestRes` 상태 변경을 추적해야 한다.

## 5. CSBehaviour.Response

`CSBehaviour.Response @ 016dcd50`는 직접 데이터를 해석하기보다는 등록된 callback으로 전달하는 역할에 가깝다.

```text
CSBehaviour.Response
  ↓
ActionExtensions.SafeInvoke
  ↓
등록 callback
```

실제 게임 데이터 처리의 핵심은 `NetworkCenter.TryHandleResponse` 이후 `DataCenter.ProccessRequestRes` 쪽이다.

## 10. 2026-09-29 ProtocolGame_SendRequest 실제 OpInfo 분석

PR.txt 원본 Listing을 직접 확인하여 각 요청 함수의 OpInfo 생성과 RequestOp 전달값을 확인했다.

### 10.1 공통 구조

각 요청 함수는 공통적으로:

```text
OpInfo::.ctor @ 015ab228
    ↓
OpInfo field assignment
    ↓
SingletonBehaviour<CSBehaviour>.Instance
    ↓
CSBehaviour.RequestOp @ 016dcafc
```

OpInfo + 0x14는 요청 opcode를 저장하는 필드로 반복 확인된다.

### 10.2 Game Server Login

대상: ProtocolGame_SendRequest.Login @ 00dde818

확인된 assignment:

| OpInfo offset | 값/동작 | 근거 |
|---|---|---|
| +0x14 | 0x02 | strh w8,[x19,#0x14], w8=2 |
| +0x28 | SystemInfo.deviceModel | get_deviceModel 후 저장 |
| +0x50 | AndroidUtils.GetSignatureMD5Hash() 결과 | 호출 후 저장 |

그 후 CSBehaviour.RequestOp(this, OpInfo)로 전달된다.

따라서 Game Server Login opcode = 0x02는 현재 Listing으로 확정할 수 있다.

Token은 이 함수에서 직접 OpInfo field로 기록되지 않는다. 현재 증거상 HTTP 로그인 단계에서 저장된 Token과 Game Server Login의 device/signature 정보는 서로 다른 계층이다.

### 10.3 GetSections

대상: ProtocolGame_SendRequest.GetSections @ 00ddea78

```text
argument: w0
OpInfo +0x14 = 0x13
OpInfo +0x30 = argument
RequestOp(OpInfo)
```

GetSections opcode = 0x13이며 요청 payload에 32-bit 인자 1개가 들어간다. 해당 인자의 게임 의미는 현재 단계에서 확정하지 않는다.

### 10.4 GetMails

대상: ProtocolGame_SendRequest.GetMails @ 00de0298

```text
OpInfo +0x14 = 0x2D
별도 payload field assignment 없음
```

GetMails opcode = 0x2D이며 현재 Listing상 추가 request parameter가 없는 zero-payload 요청이다.

### 10.5 CreateBattle

## 11. 2026-09-29 NetworkCenter → TCPTube 실제 송신 경로 분석

### 11.1 NetworkCenter.Send에서 Request 생성

`Alioth.S1.Net.NetworkCenter.Send @ 015b3764`의 Listing에서 다음 흐름이 확인된다.

```text
CSBehaviour.RequestOp(OpInfo)
    ↓
NetworkCenter.Send(OpInfo)
    ↓
기존 Queue에서 같은 OpCode Request 검색
    ↓
중복이 아니면 Request::.ctor(OpInfo)
    ↓
Request Queue.Enqueue(Request)
```

기존 Queue의 각 Request에 대해 `Request.get_Req()` 후 `Req + 0x14`를 비교한다. 따라서 `OpInfo + 0x14`의 opcode가 Request 중복 판단에도 사용된다.

### 11.2 Request::.ctor에서 확인된 필드

`Request::.ctor @ 015b3c1c`의 실제 assignment는 다음과 같다.

```text
Request::.ctor(OpInfo x20)

Request.CreateAt = DateTime.Now
Request.FinishAt = ...
Request.ID = OpInfo + 0x10
Request.Req = OpInfo
```

따라서 현재 구조는 다음과 같이 정리할 수 있다.

```text
Request
 +0x10  ID
 ...
        Req → OpInfo
```

`Request.ID`는 `OpInfo + 0x10`에서 복사된다. 따라서 `OpInfo +0x10`은 Serial/Request ID 후보로 기록한다. 정확한 C# property 이름은 `OpInfo` getter/setter 확인 전까지 최종 확정하지 않는다.

### 11.3 TrySendRequest에서 실제 Tube 선택

`NetworkCenter.TrySendRequest @ 015b3df8`는 Queue의 첫 Request를 확인한 뒤:

```text
Request.get_Req()
    ↓
Req + 0x14 (OpCode)
    ↓
Tube 목록에서 해당 OpCode handler 검색
    ↓
virtual Send 호출
```

형태로 동작한다.

또한 Request의 SendAt을 확인하고 일정 시간 이상 경과한 Request를 처리한다. 핵심은 `TrySendRequest` 자체가 protobuf 직렬화를 수행하지 않고 실제 byte 생성은 Tube의 `Send` 단계에서 수행된다는 점이다.

### 11.4 TCPTube.Send에서 protobuf 직렬화 확인

`Alioth.S1.Net.TCPTube.Send @ 015b61c8`에서 명확하게:

```text
ProtoBuf.Serializer.Serialize<object> @ 017cfc64
```

호출이 확인된다.

즉:

```text
OpInfo
 ↓
Request
 ↓
Request.get_Req()
 ↓
TCPTube.Send
 ↓
ProtoBuf.Serializer.Serialize
```

순서로 요청 객체가 직렬화된다.

따라서 `OpInfo +0x30/+0x34/+0x38`에 들어간 u32 값들은 최종적으로 protobuf serialization 대상 객체의 데이터가 된다.

### 11.5 TCPTube 송신 프레임 구성

`TCPTube.Send` Listing에서 다음 순서가 확인된다.

```text
1. OpInfo 객체를 ProtoBuf Serializer로 직렬화
2. TCPConvID 획득
3. TCPConvID를 BitConverter.GetBytes()로 변환
4. 송신 buffer에 8 bytes 기록
5. 4-byte length 영역 기록/예약
6. 0x80 기록
7. Tools.EncryptUnSafe() 호출
8. 암호화 결과를 송신 buffer에 결합
```

핵심 assembly는 다음과 같다.

```text
TCPConvID
  ↓
BitConverter.GetBytes(...)
  ↓
writer(..., length=8)

0
  ↓
BitConverter.GetBytes(...)
  ↓
writer(..., length=4)

0x80
  ↓
writer(...)

Tools.EncryptUnSafe(...)
```

이후 `Buffer.BlockCopy(...)`로 4-byte length 영역에 계산된 값이 기록된다.

따라서 현재 Listing으로 안전하게 표현할 수 있는 frame 후보는:

```text
+00  [8 bytes]  TCPConvID
+08  [4 bytes]  FrameLength
+0C  [1 byte ]  Command = 0x80 (CmdEncrypt)
+0D  [N bytes]  encrypted payload
```

이다.

Listing의 `sub w0,w22,#0xc` 및 length bytes를 offset 8에 복사하는 흐름 때문에 `FrameLength`는 전체 frame 길이에서 12를 뺀 값으로 계산되는 것으로 보인다. 이는 `0x80` command와 encrypted payload를 포함하는 길이로 해석할 수 있으나, 서버 측 parser를 확인하기 전까지 protocol 의미는 최종 확정하지 않는다.

### 11.6 CmdEncrypt와 EncryptUnSafe 관계

현재 명확히 확인된 것은:

```text
Commands.CmdEncrypt = 0x80
```

이며 `TCPTube.Send`가 `0x80`을 frame command 영역에 기록한 뒤:

```text
Tools.EncryptUnSafe @ 015af0c8
```

를 호출한다.

`EncryptUnSafe`의 caller는:

```text
KCPTube.Send
TCPTube.Send
```

로 확인된다.

따라서 현재 구조는:

```text
CmdEncrypt(0x80)
    +
EncryptUnSafe(...)
```

로 연결된다.

단, `EncryptUnSafe` 내부의 실제 암호 알고리즘과 key 사용 방식은 별도 분석 대상이다. 현재 단계에서는 특정 암호 알고리즘 이름으로 단정하지 않는다.

### 11.7 현재까지 확정된 실제 송신 chain

```text
ProtocolGame_SendRequest.GetMails()
        │
        │ OpInfo { OpCode=0x2D }
        ↓

        ↓
```

## 13. 2026-09-29 TCPTube 수신 프레임 parser 확인

### 13.1 TryRead에서 실제 frame header 확인

`Alioth.S1.Net.TCPTube.TryRead @ 015b6d54`의 assembly를 확인한 결과, 앞서 송신부에서 추정한 header 구조가 수신부에서도 직접 사용된다.

`byte[]`의 실제 data 시작 offset을 IL2CPP 배열 layout 기준 `+0x20`으로 보면:

```text
data[0..7]   = TCPConvID / UInt64
 data[8..11]  = FrameLength / Int32
 data[12]     = Command / flags byte
 data[13..]   = payload
```

TryRead에서:

```text
BitConverter.ToInt32(buffer, 0)
```

형태가 아니라 실제 data 영역 기준으로 4-byte length를 읽고, 이후 payload 길이를 계산한다.

핵심 흐름은:

```text
read 4-byte FrameLength
        ↓
필요한 전체 frame 확보
        ↓
header command/flags byte 확인
        ↓
TCPConvID 확인
        ↓
payload 추출
```

### 13.2 CmdEncrypt = 0x80 실제 수신 처리

TryRead의 실제 분기는 다음과 같다.

```text
flags byte
   │
   ├─ bit 7 (0x80) set
   │       ↓
   │   TCPTube.get_Key()
   │       ↓
   │   Tools.DecryptUnSafe()
   │       ↓
   │   clear 0x80
   │
   └─ bit 6 (0x40) set
           ↓
       Tools.DecompressUnSafe()
           ↓
       clear 0x40
```

실제 assembly:

```text
015b6ff0  TCPTube.get_Key()
015b701c  Tools.DecryptUnSafe()
015b7028  flags ^= 0x80

015b705c  Tools.DecompressUnSafe()
015b706c  flags ^= 0x40
```

그 다음:

```text
ProtoBuf.Serializer.Deserialize<object> @ 017cec0c
```

가 호출되고 결과 객체가 output reference에 저장된다.

따라서 응답 데이터 처리의 실제 핵심 chain은 현재 확정할 수 있다.

```text
TCP frame
 ↓
FrameLength
 ↓
TCPConvID
 ↓
flags
 ↓
if 0x80:
    get_Key()
    DecryptUnSafe()
    clear 0x80
 ↓
if 0x40:
    DecompressUnSafe()
    clear 0x40
 ↓
ProtoBuf.Deserialize()
 ↓
OpInfo object
```

### 13.3 일반 response의 TCPConvID 검증

TryRead 후반부에서 현재 `TCPConvID`와 수신 frame의 UInt64를 비교하는 로직도 확인된다.

즉:

```text
received TCPConvID
        ↓
TCPTube.get_TCPConvID()
        ↓
동일 여부 확인
        ↓
일치하면 payload 처리
```

이로써 `TCPConvID`는 단순 로그용 값이 아니라 실제 frame association에 사용되는 값임을 확인했다.

### 13.4 기존 PCAP handshake와 정확히 연결되는 부분

`TCPTube.TryOutput @ 015b71b0`에서는 handshake frame에 대해:

```text
data[12] == 0x01
FrameLength == 0x19
```

조건을 확인하고:

```text
data[13..20] → TCPConvID
 data[21..28] → DH public value #1
 data[29..36] → DH public value #2
```

를 읽는다.

이 구조는 기존 PCAP validator에서 확인했던 서버 handshake:

```text
payload size = 37 bytes
length       = 0x19
marker       = 0x01
TCPConvID    = 0x632
serverPub1   = <REDACTED>
serverPub2   = <REDACTED>
```

와 정확히 구조적으로 일치한다.

따라서 기존 PCAP의 `37 bytes / 0x19 / marker 1 / TCPConvID` 관찰은 이제 단순한 패킷 패턴이 아니라 **Ghidra의 실제 `TCPTube.TryOutput` parser/handshake assignment와 연결된 증거**가 되었다.

### 13.5 정상 요청/응답 frame의 현재 확정 구조

현재 증거를 합치면 정상적인 encrypted request/response frame은 다음 구조로 정리할 수 있다.

```text
offset  size       meaning
------  ---------  --------------------------------
0x00    8          TCPConvID (UInt64)
0x08    4          FrameLength (Int32)
0x0C    1          flags / command
0x0D    N          encrypted or compressed payload
```

송신:

```text
OpInfo
 ↓
ProtoBuf.Serialize
 ↓
header 생성
 ↓
flags |= 0x80
 ↓
EncryptUnSafe(key, payload)
 ↓
TCP
```

수신:

```text
TCP
 ↓
header parser
 ↓
if flags & 0x80:
    DecryptUnSafe(key, payload)
 ↓
if flags & 0x40:
    DecompressUnSafe(payload)
 ↓
ProtoBuf.Deserialize<OpInfo>
```

현재까지는 이 구조가 가장 강하게 증명된 네트워크 protocol layer다.

## 16. 2026-09-29 TryHandleResponse → DataCenter 실제 분기 확인

`NetworkCenter.TryHandleResponse @ 015b41e0` 전체 Listing을 다시 확인한 결과, `DataCenter.ProccessRequestRes` 호출 직전의 값 생성 과정이 조금 더 명확해졌다.

핵심 구간:

```text
Tube 목록 순회
 ↓
virtual response handler 호출 @ 015b43f8
 ↓
sp+0x44 = 상태/결과 byte
sp+0x48 = OpInfo/response object
 ↓
status byte < 5
 ↓

```

실제 assembly:

```text
015b43f8  blr x8
015b43fc  tbz w0,#0x0,0x015b4374
015b4400  ...
015b4414  ldrb w20,[sp,#0x44]
015b4418  cmp w20,#0x5

015b4430  mov x2,xzr
```

따라서 `ProccessRequestRes`가 단순히 모든 response를 무조건 처리하는 함수가 아니라, 앞단 response handler가 생성한 상태 byte가 `0~4`인 경우 호출되는 구조임을 확인했다.

이후에는 Request Queue의 첫 Request를 꺼내:

```text

   ↕
response/request ID
```

를 비교하고 일치하면 `Request.SetResponse(response)`가 호출된다.

또한 callback dispatch는 `Request` 처리 뒤 별도의 delegate invocation으로 이어진다.

```text

        ↓

        ↓

        ↓

```

### 16.1 중요한 의미

현재까지의 구조를 보면 `DataCenter.ProccessRequestRes`는 **protobuf parsing 함수가 아니다.** 이미 `TCPTube.TryRead`에서 protobuf deserialize가 끝난 `OpInfo` 객체를 받아 게임 데이터/state 갱신 단계로 넘기는 함수다.

즉 실제 hook 후보를 계층별로 나누면:

```text
[TCP raw]
  TCPTube.TryRead
       ↓
[decrypt/decompress]
       ↓
[protobuf]
  ProtoBuf.Deserialize
       ↓
[protocol object]
  OpInfo
       ↓
[request matching]
  NetworkCenter.TryHandleResponse
       ↓
[game state]
  DataCenter.ProccessRequestRes
       ↓
[feature callback/UI]
```

따라서 향후 Frida에서 실제 req/rsp 값을 수집하려는 목적이라면 `DataCenter.ProccessRequestRes`와 `ProtoBuf.Deserialize` 두 지점을 함께 관찰하는 것이 유용하다. 전자는 이미 구조화된 게임 response이고, 후자는 protocol object가 만들어지는 경계다.

### 16.2 현재 미확정 사항

`sp+0x44`의 상태값 `0~4`가 정확히 어떤 enum인지, `sp+0x48` 객체의 정확한 C# 타입/field mapping은 현재 Listing만으로 최종 명명하지 않는다.

다음 정적 분석에서는 response handler가 호출되는 virtual interface와 그 구현체를 추적하여 이 상태값의 enum 및 `OpInfo`의 response fields를 확인한다.

## 17. 2026-09-29 TryHandleResponse의 실제 response handler 호출 구조

`015b41e0_Alioth.S1.Net.NetworkCenter__TryHandleResponse.txt` 전체 Listing을 확인한 결과, `DataCenter.ProccessRequestRes` 앞단에서 Tube별 response handler가 virtual call로 response object와 상태 byte를 생성한다.

### 17.1 Tube 목록 순회

`NetworkCenter.get_Tubes @ 015b2e84` 후 List Enumerator로 각 Tube를 순회한다.

### 17.2 실제 virtual response handler 호출

핵심 구조:

```text
Tube object
  ↓
handler table / function pointer 탐색
  ↓
blr x8 (virtual response handler)
  ├─ return bool
  ├─ sp+0x44 = status/result byte
  └─ sp+0x48 = response object
```

실제 assembly에서 `x3 = sp+0x44`, `x4 = sp+0x48`을 넘긴 뒤 `blr x8`을 호출한다. 따라서 이 함수가 response 처리 결과와 구조화된 response object를 만들어 반환하는 계층임을 확인했다.

### 17.3 status 값에 따른 DataCenter 진입

`sp+0x48`이 NULL이 아니면 `sp+0x44`의 byte를 읽고 `cmp w20,#0x5`를 수행한다.

```text
status < 5
  ↓
DataCenter.ProccessRequestRes(response, null)

status >= 5
  ↓
별도 error/notification callback 경로
```

`0~4`의 정확한 C# enum 명칭은 아직 확정하지 않는다. 현재 Listing으로 확정 가능한 것은 `status < 5`일 때 DataCenter 경로로 들어간다는 사실이다.

### 17.4 DataCenter 이후 Request matching

정상 경로는 다음과 같다.

```text
DataCenter.ProccessRequestRes(response, null)
  ↓
Request Queue.Peek()
  ↓
Request.get_ID()
  ↓
response object +0x10과 비교
  ↓
일치하면 Queue.Dequeue()
  ↓
Request.SetResponse(response)
  ↓
callback delegate
```

실제 `015b4460`에서 response object의 `+0x10`을 읽고 `Request.get_ID @ 015b45b4` 결과와 비교한다. 따라서 response `+0x10`은 Request matching에 사용되는 response-side ID field로 확인된다.

### 17.5 Request.SetResponse 이후 callback

`Request.SetResponse @ 015b461c` 이후 NetworkCenter의 callback delegate가 호출되며, 이 호출에는 status와 현재 Request가 전달되는 구조가 확인된다.

### 17.6 실패/error 경로

`status >= 5`이면 별도 callback 경로로 분기하고, 이후 `NetworkCenter.IsRunning` 및 Request Queue cleanup으로 이어지는 코드가 존재한다. 따라서 `sp+0x44`는 단순 로그값이 아니라 정상/비정상 response 처리를 제어하는 값이다.

### 17.7 현재까지의 response 처리 구조

```text
TCP
 ↓
TCPTube.TryRead
 ↓
Decrypt / Decompress
 ↓
ProtoBuf.Deserialize
 ↓
response protocol object
 ↓
NetworkCenter.TryHandleResponse
 ↓
Tube virtual response handler
 ├─ return bool
 ├─ status @ sp+0x44
 └─ response object @ sp+0x48
 ↓
status < 5 ?
 ├─ YES → DataCenter.ProccessRequestRes → Request ID matching → SetResponse → callback
 └─ NO  → error/notification callback → queue cleanup
```

### 17.8 다음 분석 포인트

`DataCenter.ProccessRequestRes @ 016e203c` 본문은 현재 함수별 Listing 파일로 분리되어 있지 않다. 따라서 다음은 두 갈래로 진행한다.

## 19. 2026-09-29 Merge 계열 함수의 의미 재정의

게임 구조에 대한 추가 확인 결과, MergeItem / MergeEquip / MergeWeapon이라는 함수명만으로 조각을 합쳐 완제품을 자동 생성한다고 해석하거나 모두 동일한 인벤토리 처리라고 보면 안 된다.

### 19.1 조각/조합 시스템

각 Section에는 조합 가능한 완성품 목록이 존재하고, 각 완성품에 대응하는 조각 카운터가 올라간다. 조각이 기준 수량에 도달했다고 즉시 완제품이 생성되는 것이 아니라, 게임 내 재화를 사용하여 별도의 조합/제작 동작을 수행하는 구조다.

```text
Section 조합 목록
 ├─ 완성품 정의
 ├─ 필요 조각 수
 └─ 현재 조각 수
          ↓
       제작 가능
          ↓
    재화 사용/제작
          ↓
       완제품
```

### 19.2 Weapon

Weapon은 일반 Equip Inventory와 같은 의미로 취급하지 않는다. 게임상 Weapon은 캐릭터 화면에서 조합/관리되고, 완성된 무기가 캐릭터의 무기 목록에 등록되며 그중 활성 무기를 선택하는 구조다.

```text
Character
 └─ Weapon State
     ├─ unlocked / owned weapon list
     └─ active weapon
```

따라서 MergeWeapon @ 016e5be4가 실제로 어느 범위까지 갱신하는지는 assembly의 field access를 확인한 뒤 확정한다.

### 19.3 Equip

Equip은 별도 메뉴에서 관리되는 실제 인벤토리 성격의 데이터로 분리한다. MergeEquip @ 016e4348은 장비 보유/수량/상태를 서버 데이터와 병합하는 후보로 추적하되, 조각 → 완제품 제작 자체를 담당한다고 단정하지 않는다.

### 19.4 Item

Item은 현재 의미를 보류한다. Unity 데이터의 ItemInfo/ItemPackage와 서버 MergeItem @ 016e4700가 정확히 어떤 관계인지 확인해야 한다. 일반 재료/소비 아이템인지, Section별 조합 대상인지, 또는 다른 상태 데이터인지 현재 함수명만으로 결정하지 않는다.

### 19.5 현재 정적 분석에서 확인된 관계

Ali.get_dataManager @ 00e0277c의 Calls IN에 다음 함수들이 함께 나타난다.

```text
DataCenter.MergeItem            @ 016e4700
DataCenter.MergeEquip           @ 016e4348
DataCenter.MergeWeapon          @ 016e5be4
DataCenter.MergeSectionSnapShot @ 016e5908
DataCenter.UpdateHeroInfo       @ 016e4ba4
```

또한 MergeEquip/MergeWeapon 주변에는 DataTool.ToNoticeString, TipsNormalPanelMono.TipsNormalShow, HeroInfo.SuitUp, ItemShowNormalMono.SetItem 등의 관련 함수가 Calls IN으로 확인된다. 이것은 장비/무기 데이터가 UI 표시 또는 캐릭터 상태와 연결되어 있음을 보여주는 단서지만, 특정 함수가 조각 제작을 담당한다는 증거로 사용하지 않는다.

### 19.6 분석 원칙 변경

앞으로 Merge*의 의미는 이름으로 해석하지 않는다. 각 함수에서 입력 object의 실제 타입, field offset, Dictionary/List/Array 접근, DataManager/DataCache의 수정 저장소, 수량/조각/해금/활성 상태 변경 여부, Notify/UI 갱신 호출을 직접 확인한다.

최종 목표:

```text
opcode
  ↓
response object/type
  ↓
DataCenter 처리
  ↓
실제 state 저장소
  ↓
UI / Notify
```

특히 0x13 GetSections는 Section Snapshot과 조합 목록/조각 상태의 연결을 우선 확인하고, 0x16 CreateBattle은 Battle 결과와 Hero/Weapon 상태 갱신의 연결을 확인한다.


## 20. 2026-09-29 후속 작업 — ProccessRequestRes 분석 기준 확정

앞선 분석을 이어서 현재 단계의 핵심을 다음과 같이 확정한다.

### 20.1 응답 처리 경계

현재까지 실제 호출 관계는 다음과 같다.

```
TCP frame
 ↓
TCPTube.TryRead
 ↓
Decrypt / Decompress
 ↓
ProtoBuf.Deserialize
 ↓
response protocol object
 ↓
NetworkCenter.TryHandleResponse
 ↓
Tube virtual response handler
 ↓
status < 5
 ↓
DataCenter.ProccessRequestRes(response, null)
 ↓
Request ID matching / SetResponse / callback
```

따라서 `ProccessRequestRes @ 016e203c`는 protobuf 파싱 함수가 아니라, 이미 구조화된 response object를 게임 상태 계층으로 전달/반영하는 핵심 processor로 취급한다.

### 20.2 Merge 함수 해석 원칙

다음 함수들의 이름만으로 게임 기능을 의미한다고 단정하지 않는다.

| 함수 | RVA | 현재 확인 위치 | 현재 해석 |
|---|---:|---|---|
| MergeItem | 016e4700 | DataCenter/DataManager 관련 | 의미 보류 |
| MergeEquip | 016e4348 | DataCenter/DataManager 관련 | 장비 상태 병합 후보 |
| UpdateHeroInfo | 016e4ba4 | DataCenter/DataManager 관련 | Hero 상태 갱신 후보 |
| MergeSectionSnapShot | 016e5908 | DataCenter/DataManager 관련 | Section 상태 병합 후보 |
| MergeWeapon | 016e5be4 | DataCenter/DataManager 관련 | Weapon 상태 병합 후보 |

실제 의미는 입력 객체 타입, field offset, collection 접근, 저장소 변경, Notify/UI 갱신을 확인한 뒤 확정한다.

### 20.3 Section / Item / Equip / Weapon 구분

게임 동작 기준으로 현재 모델은 다음과 같이 분리해서 추적한다.

```
Section
 ├─ 완성품 목록
 ├─ 필요 조각 수
 └─ 현재 조각 수
       ↓
    제작 가능
       ↓
   게임 재화 사용
       ↓
    완성품 생성
```

Weapon은 캐릭터 화면에서 관리되는 Weapon state, Equip은 별도 메뉴의 장비 state로 분리한다. Item은 일반 재료/소비 아이템인지, Section 조합 대상인지, 다른 inventory state인지 아직 결정하지 않는다.

즉 `MergeItem = Item 조합`이라는 해석은 현재 증거로는 사용하지 않는다.

### 20.4 다음 실제 분석 순서

1. `ProccessRequestRes @ 016e203c` 주변 원본 Listing 확보
2. opcode/response type별 분기 확인
3. `MergeSectionSnapShot @ 016e5908` 입력 object와 실제 field access 확인
4. `MergeItem @ 016e4700` 입력 object와 저장소 확인
5. `UpdateHeroInfo @ 016e4ba4` 입력 object와 Hero state 확인
6. `MergeEquip @ 016e4348`, `MergeWeapon @ 016e5be4` 동일 방식 분석
7. `GetSections(0x13)` → Section response → Section state 연결 확인
8. `GetMails(0x2D)` → Mail response 연결 확인
9. `CreateBattle(0x16)` → Battle/Hero/Weapon state 변경 연결 확인

### 20.5 현재 작업의 최종 목표

단순 opcode 목록이 아니라 다음 contract를 확보한다.

```
request opcode
   ↓
protobuf request
   ↓
server response
   ↓
response object/type
   ↓
DataCenter.ProccessRequestRes
   ↓
Merge / Update
   ↓
실제 DataManager/DataCache state
   ↓
UI / Notify
```

이 contract가 확보되면 이후 네트워크 응답값 수집용 hook 위치를 기능별로 결정할 수 있고, Section 조합/조각/완성품과 Item/Equip/Weapon state의 관계도 추측이 아닌 코드 근거로 정리할 수 있다.

### 22.5 다음 작업 방향

정적 Listing만으로 함수 본문이 제공되지 않는 부분은 더 이상 함수명을 기준으로 추측하지 않는다. 다음 단계에서는 실제 실행 가능한 분석 입력에서 response object를 잡아 타입과 ID를 먼저 확정하는 것이 효율적이다.

우선 대상은 `GetSections(0x13)`이다.

1. 게임에서 GetSections 요청 직전/직후의 request ID를 확인한다.
2. 서버 response의 response-side ID(`+0x10`)를 확인한다.
3. `ProtoBuf.Deserialize` 직후 response object의 실제 타입을 확인한다.
4. 같은 response가 `ProccessRequestRes`에서 어떤 state merge로 들어가는지 hook/trace한다.
5. Section Snapshot의 실제 필드에서 fragment count, required count, completion/creation 상태를 구분한다.
