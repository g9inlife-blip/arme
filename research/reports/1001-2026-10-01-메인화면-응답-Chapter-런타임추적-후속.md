# 1001-2026-10-01 메인화면 응답 / Chapter 런타임 추적 후속

## 1. 작업 목적

1001-1의 다음 단계로 **던전 보상부터 다시 추적하지 않고 로그인 이후 메인화면에서 서버가 내려주는 상태 데이터**를 먼저 추적한다.

목표 흐름:

```
로그인
 ↓
세션/로그인 정보
 ↓
메인화면 진입
 ↓
서버 응답
 ↓
Deserialize
 ↓
OpInfo
 ├─ Items
 ├─ Weapons
 ├─ Equipments
 ├─ Chapters
 └─ Sections
 ↓
메인화면 UI 표시
```

핵심은 `OpInfo.Chapters`와 `ProtoChapter.BoxStatus`가 실제 response 처리 과정에서 어떻게 연결되는지 확인하는 것이다.

## 2. 현재까지 확정된 구조

### 2.1 ProtoChapter

Ghidra Listing 기준:

```
ProtoChapter +0x10 = Id
ProtoChapter +0x14 = Status
ProtoChapter +0x18 = Progress
ProtoChapter +0x1C = BoxStatus
```

`IsBoxReceived`는 다음 논리로 동작한다.

```
(BoxStatus & mask) != 0
mask = 1 << boxIndex
```

따라서 BoxStatus는 Box 획득 여부 bitmask로 확정한다.

### 2.2 OpInfo

```
OpInfo +0xC0 = Chapters
```

getter/setter Listing으로 offset은 확정되었다.

현재 `ProccessRequestRes @ 016e203c`의 확보된 구간에서는 Items/Weapons/Equipments/Sections 접근은 확인되었지만 Chapters 직접 접근은 아직 독립 Listing에서 확인하지 못했다.

## 3. Chapter Dictionary 연결점 추가 확인

이번 단계에서 `BattleMapMono$$LayChapterItem @ 00e4f918`의 참조 관계를 다시 확인했다.

기존 분석 기록상 이 함수에서는:

```
ChapterData의 ID
    ↓
Dictionary 조회
    ↓
ProtoChapter
    ↓
Chapter UI 구성
```

형태의 연결이 확인된다.

또한 `ProtoChapter$$IsBoxReceived @ 015acfe8`의 Calls IN에:

```
ChapBoxMono$$LayBoxItem
BattleMapMono$$LayChapterItem
BattleSectionMono$$SetStageBoxAndBar
```

가 존재한다.

즉 Chapter UI에서 실제 서버 상태 객체인 ProtoChapter를 소비하는 경로는 확인되었다.

## 4. 네트워크 Deserialize 경로

Ghidra Listing:

```
Alioth.S1.Net.KCPTube$$TryRead
        ↓
DecryptUnSafe
        ↓
ProtoBuf.Serializer$$Deserialize<object> @ 017cec0c
        ↓
response object
```

`TCPTube$$TryRead`에서도 동일한 Deserialize 호출이 확인된다.

따라서 현재 네트워크 처리 구조는:

```
KCP/TCP message
 ↓
Decrypt
 ↓
Deserialize<object>
 ↓
OpInfo/response object
 ↓
NetworkCenter.TryHandleResponse
 ↓
DataCenter.ProccessRequestRes
```

까지 연결할 수 있다.

## 5. Runtime hook 현재 상태

`research/justice_hook.js`에는 다음 추적이 이미 추가되어 있다.

```
NetworkCenter.TryHandleResponse
DataCenter.ProccessRequestRes
OpInfo.get_Chapters
ProtoChapter.get_BoxStatus
ProtoChapter.set_BoxStatus
Dictionary<int, ProtoChapter> enumeration
```

특히 `ProccessRequestRes` 진입 시:

```
response = OpInfo
response +0xC0
    ↓
Chapters Dictionary
    ↓
Dictionary entry
    ↓
ProtoChapter
    ↓
Id / BoxStatus
```

를 직접 확인하도록 되어 있다.

따라서 다음 실제 실행에서 메인화면 진입 직후 발생하는 response를 잡으면 Chapter 객체의 실제 메모리 주소와 상태값까지 연결할 수 있다.

## 6. 중요한 방향 전환

이전에는 다음을 집중 추적했다.

```
GetChapterBoxReward
 ↓
opcode 0x14
 ↓
BoxStatus
```

현재 BoxStatus의 의미 자체는 이미 PCAP + 정적 분석으로 확정되었다.

따라서 이제 핵심 질문은:

```
0x14 response
 또는
메인화면 초기 상태 response
        ↓
Deserialize<object>
        ↓
OpInfo.Chapters
        ↓
Dictionary<int, ProtoChapter>
        ↓
ProtoChapter +0x1C
```

중간의 실제 객체 생성/대입 지점이 어디인가이다.

특히 사용자가 처음 정한 순서대로 **로그인 이후 메인화면 상태 데이터부터** 확인한다.

## 8. 현재 결론

확정:

- `ProtoChapter +0x1C = BoxStatus`
- `OpInfo +0xC0 = Chapters`
- `BoxStatus`는 Box 획득 bitmask
- `BattleMapMono.LayChapterItem` → Chapter ID 기반 Dictionary → ProtoChapter 소비 경로 확인
- KCP/TCP → decrypt → `ProtoBuf.Serializer.Deserialize<object>` 경로 확인
- runtime hook은 `ProccessRequestRes / Chapters / BoxStatus`까지 준비됨

미확정:

- 실제 response object가 `OpInfo.Chapters`에 대입되는 정확한 코드
- `ProtoChapter` 객체가 생성/채워지는 정확한 protobuf 내부 경로
- 메인화면 최초 response에서 Chapters가 언제 포함되는지
- 해당 response의 OpCode와 메인화면 표시 항목의 1:1 대응

## 6. 2026-10-01 로그인 직후 메인화면 response 추적 보강

기존 hook은 `NetworkCenter.TryHandleResponse → DataCenter.ProccessRequestRes → OpInfo.Chapters → ProtoChapter.BoxStatus`까지 확인하도록 구성되어 있었다.

이번 단계에서 목표를 **로그인 직후 response 순번 + OpCode + ReturnCode + 주요 OpInfo state 포인터**로 확장했다.

### Runtime hook v4.14 추가

`research/justice_hook.js`에 다음 로그를 추가했다.

```text
[BOOT_RESP] seq=N response=... OpCode=... ReturnCode=...
[BOOT_STATE] User@+0x88=...
[BOOT_STATE] Heros@+0x90=...
[BOOT_STATE] Items@+0x98=...
[BOOT_STATE] Chapters@+0xc0=...
```

정적 Listing으로 다음 offset은 직접 확인된다.

| OpInfo field | offset | 근거 |
|---|---:|---|
| ReturnCode | +0x18 | `OpInfo$$get_ReturnCode @ 015aac7c` |
| OpCode | +0x14 | `OpInfo$$get_OpCode @ 015aac6c` |
| User | +0x88 | `OpInfo$$get_User @ 015aad7c` |
| Heros | +0x90 | `OpInfo$$get_Heros @ 015aad8c` |
| Items | +0x98 | `OpInfo$$get_Items @ 015aad9c` |
| Chapters | +0xc0 | `OpInfo$$get_Chapters @ 015aadec` |

따라서 다음 실제 실행에서 response마다 최소한 아래를 한 줄로 상관시킬 수 있다.

```text
response object
→ OpCode
→ ReturnCode
→ User/Heros/Items/Chapters 존재 여부
```

### 재화 추적

메인화면에서 실제 표시되는 재화는 `UserInfo` 계층도 함께 확인해야 한다.

Ghidra에서 `UserInfo$$get_Coins @ 00dd2d8c`가 확인되며, 이 함수는 내부 값을 직접 읽기보다 `DataCenter$$GetXCount @ 016defb0`를 호출한다.

따라서 hook에는 다음 getter 관찰을 추가했다.

```text
[MAIN_CURRENCY] Coins=...
[MAIN_CURRENCY] Energy=...
[MAIN_CURRENCY] Exp=...
[MAIN_CURRENCY] Level=...
```

이는 인증 Token 자체를 출력하지 않고, 로그인 이후 실제 메인화면 상태가 읽히는 시점을 확인하기 위한 것이다.
