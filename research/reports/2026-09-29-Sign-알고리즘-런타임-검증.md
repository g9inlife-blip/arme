# JusticeSchool Sign() 서명 알고리즘 런타임 검증 정리

- 작성일: 2026-09-29
- 대상: `com.Alioth.JusticeSchool.cn`
- 관련 스크립트: `research/justice_hook.js`
- 관련 함수: `ProtocolGame_HttpRequest.Sign`
- 관련 암호 함수: `AliothEngine.Encrypt.MD5HashString`
- 관련 .NET 함수: `System.String.Join`
- 현재 hook 버전: v4.4

---

## 1. 작업 목적

로그인 요청에 사용되는 `ProtocolGame_HttpRequest.Sign()`의 실제 서명 생성 과정을 런타임에서 확인하고, Ghidra의 정적 분석 결과와 대조하여 서명 알고리즘을 확정한다.

이번 단계에서는 단순히 `Sign()`의 반환 결과를 보는 것이 아니라 다음 지점을 직접 후킹했다.

1. `ProtocolGame_HttpRequest.Sign(content, dict)`
2. `AliothEngine.Encrypt.MD5HashString(string)`
3. `System.Convert.ToBase64String`
4. `System.String.Join` 후보

특히 MD5 함수에 실제로 전달되는 문자열을 확보함으로써 서명 생성에 사용되는 값의 순서와 구분자를 런타임에서 검증했다.

## 4. Ghidra 정적 분석 결과

`ProtocolGame_HttpRequest.Sign`의 decompile에서 확인된 흐름은 다음과 같다.

1. `content`가 null 또는 빈 문자열이면 종료
2. dictionary가 null 또는 비어 있으면 종료
3. dictionary의 Keys를 가져온다.
4. `Enumerable.OrderBy`를 사용한다.
5. 정렬된 key를 순회한다.
6. 각 key에 대응하는 dictionary value를 가져온다.
7. value들을 List에 추가한다.
8. 마지막에 `content`를 추가한다.
9. `String.Join`으로 하나의 문자열을 만든다.
10. `AliothEngine.Encrypt.MD5HashString`을 호출한다.
11. 결과를 `dict["sign"]`에 저장한다.

Ghidra에서 확인된 주요 문자열:

```text
StringLiteral_19095 = "sign"
StringLiteral_1482  = "90f04cb7a1fa5c2f58ca19cde2a2b128"
```

구분자에 해당하는 `StringLiteral_1096`은 정적 분석만으로 문자열 값이 바로 확인되지는 않았으나, MD5 hook의 실제 입력으로 구분자가 `.`임이 런타임에서 확인되었다.

## 8. 현재 확정된 Sign() 알고리즘

현재까지의 정적 분석 + 런타임 결과를 종합하면 알고리즘은 다음과 같다.

```text
Sign(content, dict):

    keys = dict.Keys
    keys = keys sorted ascending

    values = []

    for key in keys:
        values.Add(dict[key])

    values.Add(content)

    joined = String.Join(".", values)

    sign = MD5HashString(joined)

    dict["sign"] = sign
```

의사코드로 표현하면:

```text
keys = sort(dictionary.keys)

joined =
    dictionary[keys[0]]
    + "."
    + dictionary[keys[1]]
    + "."
    + ...
    + "."
    + dictionary[keys[n]]
    + "."
    + content

sign = MD5(joined)

dictionary["sign"] = sign
```

### 핵심 규칙

- dictionary의 key 자체를 MD5에 넣지 않는다.
- key를 문자열 기준 오름차순으로 정렬한다.
- 정렬된 key의 value만 사용한다.
- value 사이의 구분자는 `.`이다.
- `content`는 모든 dictionary value 뒤에 마지막으로 추가된다.
- 최종 문자열 전체를 MD5 처리한다.
- 결과를 `sign` key에 넣는다.

## 9. 빈 문자열 처리 확인

두 번째 호출에서:

```text
method = ""
```

였기 때문에 MD5 원문에 다음과 같은 부분이 나타난다.

```text
...witchwind3.logout.google...
```

즉 `method`의 빈 value도 제거하지 않고 그대로 Join에 포함한다.

따라서:

```text
A + "." + "" + "." + B
```

형태가 실제로:

```text
A..B
```

가 된다.

이것은 실제 MD5 입력에서 확인되었다.

## 10. 이전 해석에서 수정해야 할 부분

초기에는 `Sign()` 내부의 `b__40_0` 때문에 별도의 정렬 규칙이 있을 가능성을 고려했다.

하지만 이번 런타임 결과에서는 두 호출 모두 다음 규칙이 정확히 일치한다.

```text
dictionary key
    ↓
문자열 오름차순 정렬
    ↓
정렬된 key의 value
    ↓
content
    ↓
"." Join
    ↓
MD5
```

따라서 현재 단계에서는 `b__40_0`이 일반적인 identity key selector(`x => x`)일 가능성이 매우 높다.

다만 코드 수준에서 완전히 확인하려면 다음 Ghidra 함수를 직접 확인하면 된다.

```text
ProtocolGame_HttpRequest.<>c.<Sign>b__40_0
```

## 11. String.Join hook의 현재 상태

현재 `justice_hook.js v4.3`은 다음 overload를 찾으려고 했다.

```text
System.String.Join(string, object[])
```

그러나 실제 런타임에는:

```text
System.String.Join(string, string[])
@ 0x753a587b84
```

가 존재한다.

따라서 현재 Join hook은 설치되지 않았다.

다만 MD5HashString hook에서 최종 Join 결과를 직접 확보했기 때문에, Sign 알고리즘 자체의 핵심 규칙을 확인하는 데는 문제가 없었다.

### 다음 코드 수정 대상

다음 단계에서는 Join hook을:

```text
System.String.Join(string, string[])
```

기준으로 변경한다.

현재 구현되어 있는 `readIl2cppArrayStrings`를 이용하면 string[]의 각 문자열을 직접 출력할 수 있으므로, 다음 정보를 별도로 확인할 수 있다.

```text
[JOIN_DATA]
separator = "."
item[0] = ...
item[1] = ...
...
item[n] = content
```

## 14. 결론

현재 단계에서 `ProtocolGame_HttpRequest.Sign()`의 핵심 서명 생성 규칙은 사실상 확정되었다.

```text
Dictionary
    ↓
Keys 정렬(문자열 오름차순)
    ↓
정렬된 Key의 Value 추출
    ↓
마지막에 content 추가
    ↓
String.Join(".", values)
    ↓
MD5HashString()
    ↓
dict["sign"]
```

특히 가장 중요한 것은 **MD5HashString hook으로 게임이 실제로 계산한 입력 원문을 직접 확보했다는 것**이다.

따라서 앞으로의 분석은 Sign 알고리즘 자체를 추측하는 단계가 아니라:

1. Join 배열 직접 확인
2. `b__40_0` 정적 확인
3. 로컬 MD5 독립 재현
4. 실제 HTTP 로그인 요청의 `sign`과 비교
5. 이후 로그인 req/response 분석으로 연결

순서로 진행하면 된다.

## 15. `b__40_0` ARM64 디스어셈블리 확인 — 정렬 selector 확정

Ghidra에서 다음 함수를 직접 확인했다.

```text
ProtocolGame_HttpRequest.<>c$$<Sign>b__40_0()
```

실제 ARM64 코드는 다음과 같다.

```asm
00dddb90 e0 03 01 aa     mov x0, x1
00dddb94 c0 03 5f d6     ret
```

### 15.1 명령어 의미

ARM64 호출 규약에서 이 함수의 첫 번째 인자는 `x1`, 반환값은 `x0`로 전달된다.

따라서:

```asm
mov x0, x1
ret
```

은 입력값 `x1`을 그대로 반환하는 함수다.

C/C++ 관점으로 표현하면:

```c
return x1;
```

C#의 LINQ selector 관점에서는 사실상 다음과 동일하다.

```csharp
x => x
```

### 15.2 Sign()의 OrderBy와 연결

앞서 `Sign()`에서 확인한:

```text
Enumerable.OrderBy
    ↓
ProtocolGame_HttpRequest.<>c.<Sign>b__40_0
```

호출 관계와 결합하면 실제 코드는 개념적으로 다음과 같다.

```csharp
dictionary.Keys.OrderBy(x => x)
```

즉 별도의 해시, 난수, custom comparator 또는 다른 정렬 규칙을 사용하는 것이 아니다.

**Dictionary key 자체를 selector의 입력으로 받아 그대로 반환하고 있으므로, 기본 문자열 비교를 이용한 오름차순 정렬이 적용된다.**

### 15.3 런타임 결과와 교차 검증

이 결과는 앞서 확보한 MD5 입력과 정확히 일치한다.

첫 번째 호출:

```text
dict keys:
n, d, r, v, m

sorted:
d, m, n, r, v
```

실제 MD5 입력:

```text
d-value
.
m-value
.
n-value
.
r-value
.
v-value
.
content
```

두 번째 호출:

```text
dict keys:
n, d, r, v, m, t, u, p, method, platform, p2

sorted:
d, m, method, n, p, p2, platform, r, t, u, v
```

실제 MD5 입력도 정확히 같은 순서였다.

따라서 현재는 다음 세 가지 증거가 서로 일치한다.

```text
[Ghidra Sign()]
       │
       ├─ Keys
       │
       └─ OrderBy(b__40_0)
                    │
                    ▼
             [b__40_0]
                    │
                    ▼
              return x1
                    │
                    ▼
                x => x
                    │
                    ▼
          문자열 key 오름차순
                    │
                    ▼
[Runtime MD5 input] ──────── 동일한 순서
```

### 15.4 정적 분석 상태 변경

기존 문서에서는 `b__40_0`을 다음과 같이 기록했다.

```text
미확인 / identity selector일 가능성이 높음
```

이번 Ghidra 결과로 다음과 같이 변경한다.

```text
확인 완료
```

즉 `b__40_0`에 대한 추가적인 추측은 필요하지 않다.

## 16. 현재 Sign 분석 확정도 업데이트

현재까지 확보된 핵심 증거:

| 분석 항목 | 상태 | 증거 |
|---|---|---|
| `Sign()` 주소 | 확정 | IL2CPP 런타임 |
| Dictionary Keys 사용 | 확정 | Ghidra |
| `OrderBy` 사용 | 확정 | Ghidra |
| `b__40_0` 역할 | **확정** | ARM64 `mov x0,x1; ret` |
| 정렬 selector | **`x => x` 확정** | ARM64 |
| key 문자열 오름차순 정렬 | **확정** | 정적 + 런타임 교차검증 |
| 정렬된 key의 value 사용 | 확정 | Ghidra + MD5 input |
| `content` 마지막 추가 | 확정 | Ghidra + MD5 input |
| Join 구분자 `.` | 확정 | MD5 input |
| 빈 문자열 유지 | 확정 | 실제 `method=""` |
| MD5 계산 | 확정 | `MD5HashString` hook |
| `dict["sign"]` 저장 | 확정 | Sign 결과 |
| `String.Join(string,string[])` overload | 확정 | 런타임 |
| 실제 Join 배열 hook | 다음 단계 | 현재 JS 수정 필요 |

따라서 현재 **Sign 알고리즘의 핵심 로직은 정적 분석과 런타임 분석 양쪽에서 확정된 상태**다.

## 17. v4.4 String.Join(string,string[]) 런타임 검증 완료

`justice_hook.js`의 `String.Join` 대상 overload를 기존 `object[]`에서 실제 런타임 overload인 `string[]`으로 수정했다.

### 17.1 실제 overload 확인

게임 런타임에서 다음 overload가 확인되고 hook되었다.

```text

  (System.String, System.String[]) -> System.String
  @ 0x753a640b84

[+] Hooking System.String.Join(System.String, System.String[])
```

따라서 이전의 `object[]` 대상 오류는 제거되었다.

### 17.2 첫 번째 호출 — Join 배열 직접 확인

### 17.4 이번 단계에서 추가로 확정된 사실

이번 `string[]` 직접 hook으로 다음 사항을 추가 확정했다.

1. `String.Join`의 실제 overload는 `string,string[]`이다.
2. Join 배열의 첫 항목부터 마지막 항목까지가 `MD5HashString` 입력 순서와 정확히 일치한다.
3. `content`는 Join 배열의 마지막 항목이다.
4. 빈 문자열 `method=""`은 배열에서 제거되지 않는다.
5. 따라서 빈 값은 실제 문자열에서 `..`을 만든다.
6. `joined_preview`와 `joined_actual`이 동일하여 JS의 배열 해석도 실제 Join 결과와 일치한다.
7. `Sign()` 실행 후 dictionary에 `sign`이 추가된다.

### 17.5 현재 증거 구조

```text
Ghidra
  ↓
Dictionary.Keys
  ↓
OrderBy(x => x)
  ↓
정렬된 key의 value 추출
  ↓
String.Join(".", string[])
  ↓
[JOIN_DATA] 실제 배열
  ↓
[JOIN_DATA] joined_actual
  ↓
[MD5_DATA] input
  ↓
MD5HashString
  ↓
[MD5_DATA] output
  ↓
dict["sign"]
```

따라서 이제 `String.Join` overload 또는 Join 배열에 대한 추가 추측은 필요하지 않다.

## 18. 다음 단계 — Sign에서 최종 HTTP 요청 검증으로 이동

Sign 알고리즘은 현재 충분한 증거를 확보했으므로 다음 핵심 작업은 **서명값이 실제 HTTP 요청에 어떻게 들어가는지 확인하는 것**이다.

다음 단계에서 `V4_POST_Login` 주변을 추적하여 최소한 다음 값을 확보한다.

```text
app_key
content
apiName
GetDefaultParams() 결과
Sign() 전 dictionary
Sign() 후 dictionary
최종 sign
HTTP method
URL
query/body
headers
```

그리고 동일 로그인 시점의 PCAP과 다음 관계를 대조한다.

```text
V4_POST_Login
    ↓
GetDefaultParams
    ↓
Sign
    ↓
sign 추가
    ↓
HttpRequest 생성/전송
    ↓
PCAP TCP payload
```

목표는 단순히 Sign을 재현하는 것이 아니라 **게임이 실제 서버로 전송한 로그인 request와 hook에서 확보한 값이 1:1 대응하는지 확인하는 것**이다.
