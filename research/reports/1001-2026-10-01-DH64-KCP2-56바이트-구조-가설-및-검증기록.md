# 1001-2026-10-01 DH64 / KCP2 56바이트 구조 가설 및 검증기록

현재 로그는 원본 서버 정상 응답이 아니라 로컬 서버가 클라이언트 Handshake를 받아 자체 해석·DH 계산·응답한 결과다. 따라서 서버 parser의 필드 해석은 검증 대상이며 확정값으로 취급하지 않는다.

## 관찰
- Handshake 수신 길이: 56 bytes
- 시작부 예: `00000000000000002c00000001...`
- parser 출력 예: Peer public #1=`0xcb0b3cd581b2ed66`, #2=`0x61636f6ce755cefd`
- 여러 연결에서 #2가 `0x61636f6c...` 형태로 반복
- 로컬 서버: Peer public → session key → Server public → 56-byte 응답 → 클라이언트 종료

## 열어둘 가설
### A
Ghidra의 KCPTube Handshake2가 packet +0x11 / +0x19의 64-bit 값을 DH 입력으로 사용하는 해석과 일치하며 `0x61636f6c...`도 실제 DH public #2일 가능성.

### B
+0x19가 다른 논리 필드이고 로컬 parser가 이를 DH public #2라고 잘못 명명했을 가능성.

### C
56-byte 패킷에 상위 handshake header와 DH 관련 데이터가 함께 있으며 현재 field 경계 해석이 일부 잘못되었을 가능성.

## 현재 확인 / 미확정
확인: 56-byte Handshake 반복 수신, `0x61636f6c...` 반복, 로컬 서버의 DH/session-key 계산, 56-byte 응답 전송, 응답 후 클라이언트 종료.

미확정: +0x11/+0x19의 wire-level 의미, `0x61636f6c...`의 의미, 정확한 서버 응답 형식, server public 위치, DH 결과와 응답 field 대응, 종료 원인.

## 다음 검증 순서
1. 원본 56 bytes 전체를 offset 00~37로 분해.
2. Ghidra Handshake1/Handshake2의 실제 read 위치와 대조.
3. DH64.Secret 입력과 session key 생성 위치 대응.
4. 서버 56-byte 응답과 클라이언트가 기대하는 field를 1:1 비교.
5. 응답 직후 client parse → Handshake2 → DH/key init → KCP state transition 중 종료 지점 확인.

`0x61636f6c...`을 DH public #2가 아니라고 결론내리지 않는다. 반대로 +0x19 접근만으로 wire protocol 전체를 확정하지도 않는다. 서버 코드 수정 전에 원본 입력 → offset → Ghidra read → DH 입력 → 서버 응답 → 종료 지점을 순서대로 맞춘다.

## 로그인 흐름 분리
